# CPU 指令集架构总结

---

## 一、什么是指令集架构（ISA）

**指令集架构**（Instruction Set Architecture，ISA）是 CPU 硬件与软件之间的接口规范。它定义了：

- CPU 能执行哪些指令（加法、跳转、内存读写……）
- 指令的二进制编码格式（机器码）
- 有哪些寄存器、各自多大
- 内存如何寻址
- 数据类型和大小

**同一种 ISA 的程序可以在同一种架构的不同 CPU 上运行**。比如 Intel Core 和 AMD Ryzen 都是 x86_64 架构，编译出来的程序可以互相运行。但 x86_64 的程序不能在 ARM CPU 上运行，反之亦然。

### CISC vs RISC

ISA 按设计理念分为两大流派：

| | CISC（复杂指令集） | RISC（精简指令集） |
|--|-------------------|-------------------|
| 全称 | Complex Instruction Set Computer | Reduced Instruction Set Computer |
| 设计理念 | 一条指令完成复杂操作，指令种类多 | 每条指令只做简单操作，指令种类少 |
| 指令长度 | **变长**（1~15 字节不等） | **固定长度**（通常 4 字节） |
| 指令数量 | 数千条 | 数百条 |
| 内存访问 | 很多指令可以直接操作内存 | 只有 load/store 指令能访问内存 |
| 代表架构 | **x86、x86_64** | **ARM、RISC-V、MIPS** |

> 现代 CPU 的界限其实在模糊：x86_64 CPU 内部会把复杂的 CISC 指令拆成微操作（micro-ops），本质上内部也是 RISC 风格执行的。但从程序员看到的 ISA 层面来说，x86_64 仍然是 CISC。

## 二、主流指令集架构对比

| 维度 | x86_64 (AMD64) | ARM (AArch64) | RISC-V |
|------|----------------|---------------|--------|
| 设计理念 | CISC | RISC | RISC |
| 位宽 | 64 位 | 64 位 | 32/64/128 位 |
| 指令长度 | 变长（1~15 字节） | 固定 4 字节 | 固定 4 字节（基础） |
| 通用寄存器 | 16 个（RAX~R15） | 31 个（X0~X30） | 32 个（x0~x31） |
| 字节序 | 小端（Little-Endian） | 可配置，通常小端 | 小端 |
| 典型应用 | PC、服务器、工作站 | 手机、平板、部分服务器和 Mac | 嵌入式、学术、新兴服务器 |
| 代表芯片 | Intel Core、AMD Ryzen | Apple M 系列、高通骁龙、华为鲲鹏 | SiFive、平头哥玄铁 |
| 许可模式 | Intel/AMD 专有 | ARM 公司授权 | 完全开源 |
| 出现时间 | 1978 年（8086），2003 年（AMD64） | 1985 年（ARM1），2011 年（ARMv8/AArch64） | 2010 年（UC Berkeley） |

### 各架构的设计哲学

**x86_64**：从 1978 年的 8086 一路向后兼容演进到今天，历史包袱重，但生态最成熟。特点是"一条指令干很多事"，比如 `rep movsb` 一条指令就能完成内存块复制。

**ARM**：追求高能效比（性能/功耗），指令简洁规整。手机和平板几乎 100% 使用 ARM，近年来也开始进军服务器（AWS Graviton、Apple M 系列）。

**RISC-V**：完全开源的 ISA，任何人都可以免费设计 RISC-V CPU，被视为未来的发展方向，但目前生态还在建设中。

## 三、同一段 C 代码在不同架构/语法下的汇编对比

### 源代码

```c
int add(int a, int b) {
    return a + b;
}
```

### x86_64 —— Intel 语法

```asm
add:
    lea    eax, [rdi+rsi]    ; eax = rdi + rsi（第1个参数 + 第2个参数）
    ret                      ; 返回，结果在 eax 中
```

> 说明：x86_64 Linux 下，第 1 个整数参数在 `rdi`，第 2 个在 `rsi`。`lea` 在这里被编译器巧妙地用来做加法。

### x86_64 —— AT&T 语法（同一段机器码，不同的书写方式）

```asm
add:
    leal   (%rdi,%rsi), %eax    # %eax = %rdi + %rsi
    ret
```

> 对比 Intel 语法：寄存器加了 `%` 前缀，内存引用格式变了，指令加了 `l` 后缀表示 32 位操作。**但编译出来的机器码是一模一样的。**

### ARM64 (AArch64)

```asm
add:
    add    w0, w0, w1    // w0 = w0 + w1（第1个参数 + 第2个参数）
    ret                  // 返回，结果在 w0 中
```

> 说明：ARM64 下，第 1 个参数在 `x0`（64位）/ `w0`（低32位），第 2 个在 `x1` / `w1`。ARM 的 `add` 指令是三操作数格式：`add 目标, 源1, 源2`。

### 三者对比总结

| 特征 | x86_64 (Intel) | x86_64 (AT&T) | ARM64 |
|------|---------------|---------------|-------|
| 加法 | `lea eax, [rdi+rsi]` | `leal (%rdi,%rsi), %eax` | `add w0, w0, w1` |
| 操作数顺序 | 目标在左 | 目标在右 | 目标在左 |
| 寄存器前缀 | 无 | `%` | 无 |
| 参数寄存器 | rdi, rsi | %rdi, %rsi | x0, x1 |
| 指令风格 | 二操作数（目标=源之一） | 同 Intel（只是写法不同） | 三操作数（目标可以与源不同） |
| 机器码 | x86_64 编码 | **与 Intel 完全相同** | ARM64 编码（完全不同） |

## 四、Intel 语法 vs AT&T 语法详细对照

**这两种语法仅存在于 x86 架构中**，它们是同一套机器指令的两种人类可读写法。ARM 没有这个问题——ARM 只有一种汇编语法。

### 对照表

| 维度 | Intel 语法 | AT&T 语法 |
|------|-----------|-----------|
| **操作数方向** | `mov rax, rbx`（目标在左） | `movq %rbx, %rax`（目标在右） |
| **赋值类比** | 类似 `rax = rbx` | 类似 `rbx -> rax` |
| **寄存器前缀** | 无：`rax`, `rbp` | 有 `%`：`%rax`, `%rbp` |
| **立即数前缀** | 无：`mov rax, 42` | 有 `$`：`movq $42, %rax` |
| **内存引用** | `[rbp-8]` | `-8(%rbp)` |
| **复杂寻址** | `[rax+rcx*4+8]` | `8(%rax,%rcx,4)` |
| **大小限定** | 前置：`DWORD PTR [rbp-8]` | 指令后缀：`movl -8(%rbp)` |

### 大小后缀对照（AT&T 特有）

| AT&T 后缀 | 含义 | 对应 Intel 限定符 | 大小 |
|-----------|------|-----------------|------|
| `b` | byte | `BYTE PTR` | 1 字节 |
| `w` | word | `WORD PTR` | 2 字节 |
| `l` | long（双字） | `DWORD PTR` | 4 字节 |
| `q` | quad（四字） | `QWORD PTR` | 8 字节 |

### 完整示例对比

**C 代码**：`int x = 42;`（局部变量赋值）

Intel 语法：
```asm
mov    DWORD PTR [rbp-4], 42
```

AT&T 语法：
```asm
movl   $42, -4(%rbp)
```

两者做的事情完全一样：把 42（4 字节整数）写入栈上 `rbp-4` 的位置。

### 各自的使用场景

| Intel 语法 | AT&T 语法 |
|-----------|-----------|
| Intel/AMD 官方手册 | GNU 工具链默认（GCC、GDB、objdump） |
| NASM/MASM 汇编器 | GAS（GNU Assembler）默认 |
| Windows 开发工具 | Linux 开发工具默认 |
| IDA Pro 反汇编器 | `gcc -S` 默认输出 |

> 在 GCC 中可以用 `-masm=intel` 参数切换为 Intel 语法输出：
> ```bash
> g++ -S -masm=intel -O0 file.cpp -o file.s
> ```
>
> objdump 也可以用 `-M intel` 切换：
> ```bash
> objdump -d -M intel a.out
> ```

## 五、函数调用约定的跨平台差异

函数调用约定（Calling Convention）规定了函数之间如何传递参数、返回值、谁负责保存哪些寄存器。不同平台的约定不同。

### 整数/指针参数传递

| 平台 | 约定名称 | 参数寄存器（按顺序） | 返回值寄存器 |
|------|---------|-------------------|------------|
| x86_64 Linux/macOS | System V AMD64 ABI | RDI, RSI, RDX, RCX, R8, R9 | RAX |
| x86_64 Windows | Microsoft x64 | RCX, RDX, R8, R9（仅 4 个） | RAX |
| ARM64 (AArch64) | AAPCS64 | X0, X1, X2, X3, X4, X5, X6, X7（8 个） | X0 |

### 浮点参数传递

| 平台 | 浮点参数寄存器 | 浮点返回值 |
|------|-------------|-----------|
| x86_64 Linux/macOS | XMM0 ~ XMM7 | XMM0 |
| x86_64 Windows | XMM0 ~ XMM3 | XMM0 |
| ARM64 | V0 ~ V7（NEON/FP 寄存器） | V0 |

### 超出寄存器的参数

当参数数量超过寄存器能容纳的数量时，**多余的参数通过栈传递**（从右到左压栈）。

### 同一个函数在不同平台的调用差异示例

```c
long foo(long a, long b, long c, long d, long e, long f, long g);
// 7 个参数
```

**x86_64 Linux**（System V ABI）：

| 参数 | a | b | c | d | e | f | g |
|------|---|---|---|---|---|---|---|
| 位置 | RDI | RSI | RDX | RCX | R8 | R9 | **栈** |

6 个寄存器用完，第 7 个参数 `g` 通过栈传递。

**x86_64 Windows**（Microsoft x64）：

| 参数 | a | b | c | d | e | f | g |
|------|---|---|---|---|---|---|---|
| 位置 | RCX | RDX | R8 | R9 | **栈** | **栈** | **栈** |

只有 4 个寄存器，第 5~7 个参数都通过栈传递。

**ARM64**（AAPCS64）：

| 参数 | a | b | c | d | e | f | g |
|------|---|---|---|---|---|---|---|
| 位置 | X0 | X1 | X2 | X3 | X4 | X5 | X6 |

8 个寄存器，全部参数都通过寄存器传递。

### 调用者保存 vs 被调用者保存（以 System V AMD64 ABI 为例）

| 类别 | 寄存器 | 含义 |
|------|-------|------|
| **调用者保存**（Caller-saved） | RAX, RCX, RDX, RSI, RDI, R8~R11 | 函数调用可能会改变这些寄存器，调用者如果还需要这些值，必须在 `call` 之前自己保存 |
| **被调用者保存**（Callee-saved） | RBX, RBP, R12~R15 | 被调用函数如果要用这些寄存器，必须先保存旧值，函数返回前恢复 |

## 六、Linux 与 CPU 架构的关系

### "Linux = ARM" 是一个常见误区

**Linux 是操作系统内核，不是 CPU 架构。Linux 可以运行在几乎任何 CPU 架构上。**

| 场景 | CPU 架构 | 操作系统 |
|------|---------|---------|
| 大多数云服务器（AWS EC2、阿里云） | Intel/AMD **x86_64** | Linux（CentOS/Ubuntu） |
| AWS Graviton 服务器 | ARM **AArch64** | Linux（Amazon Linux） |
| 华为鲲鹏服务器 | ARM **AArch64** | Linux（EulerOS） |
| 手机 | ARM **AArch64** | Android（基于 Linux 内核） |
| Mac (M1/M2/M3/M4) | Apple Silicon **AArch64** | macOS（不是 Linux，但类 Unix） |
| 树莓派 | ARM | Linux（Raspberry Pi OS） |
| 我的电脑（WSL2） | AMD **x86_64** | Linux（Ubuntu on WSL2） |

同一个 Linux 发行版通常会提供多种架构的构建版本。例如 Ubuntu 有：
- `amd64` 版本：运行在 x86_64 CPU 上
- `arm64` 版本：运行在 ARM64 CPU 上
- `riscv64` 版本：运行在 RISC-V CPU 上

它们都是 Ubuntu，但编译出来的二进制文件（包括内核和所有软件包）使用的是不同的机器指令。

### 我的 WSL2 环境链条

```
┌─────────────────────────────────────────────────────────────┐
│  硬件层：AMD Ryzen 9 8940HX                                  │
│  指令集：x86_64 (AMD64)                                      │
├─────────────────────────────────────────────────────────────┤
│  宿主操作系统：Windows                                        │
│  虚拟化层：Hyper-V                                            │
├─────────────────────────────────────────────────────────────┤
│  WSL2：运行真正的 Linux 内核（x86_64 版本）                     │
│  → 直接使用宿主机的 x86_64 指令集，不存在指令翻译               │
├─────────────────────────────────────────────────────────────┤
│  用户空间：Ubuntu (amd64)                                     │
│  编译器：GCC 10.5.0 → 生成 x86_64 机器码                      │
│  汇编语法：Intel 语法（通过 -masm=intel 指定）                  │
│  调用约定：System V AMD64 ABI                                 │
└─────────────────────────────────────────────────────────────┘
```

**关键理解**：

1. WSL2 里的 Linux 内核是 **x86_64 版本**的，因为宿主机 CPU 是 x86_64。WSL2 通过 Hyper-V 虚拟化运行，但**不做指令翻译**——Linux 内核直接在 x86_64 CPU 上执行 x86_64 指令。

2. WSL2 里编译出来的程序和**任何 x86_64 Linux 服务器上编译的程序**使用完全相同的指令集和调用约定。理论上可以直接拿到 x86_64 Linux 服务器上运行。

3. 如果要在 WSL2 里运行 ARM 程序，需要额外安装 QEMU 等指令翻译器——因为 x86_64 CPU 本身不认识 ARM 指令。

### 决定汇编代码的因素

```
你写的 C/C++ 源代码
        │
        ▼
   编译器（GCC）
        │
        ├── 根据【目标 CPU 架构】决定生成什么指令集的机器码
        │   （x86_64 → mov/push/lea...  ARM → ldr/str/add...）
        │
        ├── 根据【目标操作系统】决定使用什么调用约定
        │   （Linux → System V ABI    Windows → Microsoft x64）
        │
        └── 根据【汇编语法参数】决定汇编代码的书写格式
            （-masm=intel → Intel 语法    默认 → AT&T 语法）
```

所以最终你看到什么样的汇编代码，由三个因素共同决定：**CPU 架构**、**操作系统**、**语法选项**。
