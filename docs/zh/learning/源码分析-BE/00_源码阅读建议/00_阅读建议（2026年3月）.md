# StarRocks BE 源码阅读建议（面向 Java 工程师）

> **适用版本**：branch-3.2.16（2026 年 3 月）
>
> **目标读者**：熟悉 Java、对 C++ 语法不太熟悉、希望阅读 StarRocks BE 源码的工程师。
>
> **配套文档**：建议结合 `01_项目结构分层/` 下的 5 份模块说明文档一起阅读，先建立全局地图再深入细节。

## 1. 阅读前的心理准备

### 1.1 Java 工程师读 C++ 的核心障碍

作为 Java 工程师，你会发现 C++ 代码的 **信息密度远高于 Java**。一个 `.h` 文件往往同时包含类声明、内联实现、模板定义、宏展开和类型别名，而 Java 中这些概念分散在不同的文件和注解中。以下是最常见的心理落差：

| 你在 Java 中习惯的 | 在 C++ 中遇到的 | 应对策略 |
|---|---|---|
| 一个 `.java` 文件一个类 | `.h` 声明 + `.cpp` 实现分离，一个文件可能有多个类 | **先只读 `.h`**，理解接口；`.cpp` 需要时再读 |
| 垃圾回收（GC） | 手动内存管理 / 智能指针 / RAII | 关注 `shared_ptr`/`unique_ptr`/析构函数 |
| `try-catch` 异常处理 | `Status` 返回值 + `RETURN_IF_ERROR` 宏 | 把 `Status` 当作"受检异常的返回值形式" |
| Spring 依赖注入 | 全局单例 + 指针传递 | 关注 `ExecEnv::GetInstance()` 等单例 |
| `interface` + `implements` | 纯虚函数 (`= 0`) + 继承 | `virtual void foo() = 0` ≈ Java `abstract` 方法 |
| 泛型 `<T>` | C++ 模板（编译期展开，更强大也更复杂） | 先把模板当泛型理解，遇到特化再深入 |

### 1.2 不要试图"全部读完"

BE 源码共约 **2381 个源文件、56 万行代码**。即使是核心开发者，也不会通读所有代码。正确的策略是：

1. **建立全局地图**（读本系列文档 + 目录总览）
2. **选择一条执行路径**深入跟踪（见第 5 节推荐路径）
3. **按需展开**到相关模块

## 2. 环境准备

### 2.1 编译 BE

```bash
# 编译 BE（Release 模式，首次需要 30-60 分钟）
sh build.sh --be

# 编译 BE（Debug 模式，便于调试和阅读）
BUILD_TYPE=Debug sh build.sh --be

# 编译 BE（ASAN 模式，检查内存问题）
BUILD_TYPE=Asan sh build.sh --be
```

> **建议**：首次用 Debug 模式编译，这样可以用 GDB/LLDB 进行断点调试、单步跟踪，极大加速源码理解。

> **推荐**：关于编译启动debug，可详见[编译启动debug](../../编译启动debug)之下的文档

### 2.2 IDE 配置

推荐使用以下 IDE 之一，都能提供 C++ 的代码补全、跳转定义、查找引用等功能：

| IDE | 配置要点 |
|---|---|
| **CLion** | 直接打开 `be/` 目录，CLion 会自动识别 CMakeLists.txt |
| **VS Code + clangd** | 安装 clangd 插件，BE 编译后会生成 `compile_commands.json` |
| **Cursor + clangd** | 同 VS Code，确保 clangd 扩展已启用 |

> **关键**：确保 IDE 能正确解析 `#include` 路径。如果跳转失败，检查是否已编译生成 `compile_commands.json`（通常在 `be/build/` 下）。

### 2.3 代码风格

项目使用 **Google C++ Style**（见根目录 `.clang-format`），缩进 4 空格，行宽 120 字符。了解这点有助于你习惯代码的视觉布局。

## 3. 必须先理解的 C++ 概念

以下概念在 StarRocks BE 中**出现频率极高**，建议在开始阅读源码前逐一理解。

### 3.1 头文件与实现分离（`.h` / `.cpp`）

**Java 类比**：想象每个 Java 类的 `interface` 单独放一个文件（`.h`），`class` 实现放另一个文件（`.cpp`）。

```cpp
// status.h —— 声明（≈ Java interface）
class Status {
public:
    bool ok() const;           // 只有签名，没有函数体
    static Status OK();
private:
    char* _state;              // 成员变量用 _ 前缀命名
};

// status.cpp —— 实现（≈ Java class）
bool Status::ok() const {
    return _state == nullptr;  // 函数体在这里
}
```

**阅读技巧**：在 StarRocks BE 中，**先读 `.h` 文件就足够理解一个模块的功能和边界**。`.cpp` 文件是实现细节，需要时再看。

### 3.2 `#pragma once` 和 `#include`

BE 全部使用 `#pragma once`（≈ Java 的 `package` 防重复导入），`#include` ≈ Java 的 `import`。

```cpp
#pragma once              // 防止头文件被重复包含

#include "common/status.h" // ≈ import starrocks.common.Status;
#include <memory>          // ≈ import java.lang.ref.*;（标准库用尖括号）
```

### 3.3 命名空间（namespace）

```cpp
namespace starrocks {       // ≈ package starrocks;
namespace pipeline {        // ≈ package starrocks.pipeline;
    class Operator { ... };
}
}
```

**BE 中的主要命名空间**：
- `starrocks` — 顶层命名空间，绝大部分代码都在此
- `starrocks::pipeline` — Pipeline 执行引擎
- `starrocks::lake` — 存算分离存储层

### 3.4 智能指针（重点！）

这是 Java 工程师最需要理解的 C++ 概念。C++ 没有 GC，用智能指针代替：

| C++ 智能指针 | Java 类比 | 在 BE 中的使用场景 |
|---|---|---|
| `std::shared_ptr<T>` | 普通引用（带引用计数，最后一个引用释放时自动删除） | `ColumnPtr`、`ChunkPtr`、`OperatorPtr` 等 |
| `std::unique_ptr<T>` | 没有直接对应（独占所有权，不可复制，只能移动） | `MutableColumnPtr`、`ChunkUniquePtr` |
| 裸指针 `T*` | 弱引用（不拥有对象，只是借用） | 函数参数中很常见，表示"我不管它的生命周期" |

BE 中大量使用类型别名来简化智能指针：

```cpp
// column/vectorized_fwd.h 中定义的别名
using ColumnPtr = std::shared_ptr<Column>;          // 共享列指针
using MutableColumnPtr = std::unique_ptr<Column>;   // 独占可变列指针
using ChunkPtr = std::shared_ptr<Chunk>;            // 共享 Chunk 指针
using OperatorPtr = std::shared_ptr<Operator>;      // 共享算子指针
```

> **阅读技巧**：看到 `XxxPtr` 类型时，去 `column/vectorized_fwd.h` 或相关头文件查看它是 `shared_ptr` 还是 `unique_ptr`，就能理解所有权语义。

### 3.5 RAII 模式（核心思想！）

RAII（Resource Acquisition Is Initialization）是 C++ 最重要的设计思想，**没有之一**。

**Java 类比**：`try-with-resources` 的自动化版本。C++ 的析构函数在变量离开作用域时 **自动调用**，无需 `finally` 块。

BE 中的 RAII 典型示例：

```cpp
// DeferOp —— ≈ Java 的 try-finally，但更优雅
{
    auto cleanup = DeferOp([]() { release_resource(); });
    // ... 正常逻辑 ...
    // 无论正常返回还是提前 return，cleanup 的析构函数都会调用 release_resource()
}

// ClosureGuard —— RPC 回调的 RAII 守卫
void handle_rpc(google::protobuf::Closure* done) {
    ClosureGuard guard(done);  // guard 析构时自动调用 done->Run()
    // ... 处理逻辑 ...
    // 无需手动调用 done->Run()，即使中途 return 也不会遗漏
}

// std::lock_guard —— ≈ Java synchronized，但作用域更精确
{
    std::lock_guard<std::mutex> lock(mutex_);  // 加锁
    // ... 临界区 ...
}   // lock 析构，自动解锁
```

> **记住**：在 C++ 中看到一个对象被创建但似乎"没被使用"，它很可能是 RAII 守卫——它的价值在于析构函数。

### 3.6 Status 错误处理模式（极高频！）

StarRocks BE **不使用 C++ 异常**，而是通过返回 `Status` 对象来传递错误。这套模式贯穿整个代码库：

```cpp
// 函数返回 Status 表示可能失败
Status StorageEngine::open(const EngineOptions& options, StorageEngine** engine);

// RETURN_IF_ERROR 宏 —— ≈ Java 的异常自动传播
Status init() {
    RETURN_IF_ERROR(step1());  // 如果 step1() 失败，直接 return 错误
    RETURN_IF_ERROR(step2());  // 如果 step2() 失败，直接 return 错误
    return Status::OK();
}

// StatusOr<T> —— ≈ Java 的 Optional<T> + Exception
StatusOr<ChunkPtr> read_chunk() {
    // 成功返回值，失败返回错误
}

// ASSIGN_OR_RETURN 宏 —— 解包 StatusOr
Status process() {
    ASSIGN_OR_RETURN(auto chunk, read_chunk());  // 失败则 return 错误，成功则解包赋值
    // 此处 chunk 已经是 ChunkPtr 类型
}
```

**Java 等价理解**：
```java
// Java 中你会这样写
Chunk chunk = readChunk();  // 可能抛出 checked exception

// C++ 中的等价写法
ASSIGN_OR_RETURN(auto chunk, read_chunk());  // 失败自动 return Status
```

### 3.7 虚函数与继承

```cpp
// ≈ Java abstract class
class Operator {
public:
    virtual ~Operator() = default;            // 虚析构函数（Java 不需要）
    virtual Status prepare(RuntimeState* state); // 虚函数，可被子类覆盖
    virtual bool has_output() const = 0;      // 纯虚函数（≈ Java abstract 方法）
};

// ≈ Java class ScanOperator extends Operator
class ScanOperator : public Operator {
public:
    bool has_output() const override;         // override ≈ Java @Override
};
```

### 3.8 模板（Template）

**Java 类比**：泛型 `<T>`，但 C++ 模板在编译期展开，功能远超 Java 泛型。

```cpp
// 简单模板 ≈ Java 泛型
template <typename T>
class FixedLengthColumn : public Column {  // ≈ class FixedLengthColumn<T> extends Column
    Buffer<T> _data;
};

// 使用：
FixedLengthColumn<int32_t> col;  // ≈ FixedLengthColumn<Integer> col;
```

> **阅读技巧**：初次阅读时，把 `template <typename T>` 当成 Java 的 `<T>` 泛型理解即可。遇到模板特化（`template<>`）和 SFINAE 等高级技巧时，可以先跳过。

### 3.9 常见的宏定义

BE 中有大量宏，初次遇到会困惑。以下是最常见的：

| 宏 | 含义 | Java 类比 |
|---|---|---|
| `RETURN_IF_ERROR(expr)` | 如果 expr 返回错误 Status，立即 return | 异常自动传播 |
| `ASSIGN_OR_RETURN(var, expr)` | 解包 StatusOr，失败则 return | 解包 Optional 或捕获异常 |
| `EXIT_IF_ERROR(expr)` | 如果 expr 失败，直接 `exit(1)` | 仅在启动阶段使用 |
| `UNLIKELY(expr)` | 编译器提示：这个分支不太可能执行 | 无直接对应（JIT 会自动优化） |
| `LIKELY(expr)` | 编译器提示：这个分支很可能执行 | 同上 |
| `DCHECK(expr)` | Debug 模式下的断言（Release 模式不生效） | `assert` |
| `VLOG(n)` | 按级别输出日志 | `logger.trace()` / `logger.debug()` |
| `CONF_Int32(name, default)` | 声明一个可配置的 int32 变量 | `@Value("${name}")` |
| `SCOPED_TIMER(counter)` | RAII 计时器，作用域结束自动记录耗时 | 手动 `System.nanoTime()` 计时 |

### 3.10 成员变量命名约定

StarRocks BE 的成员变量使用 **下划线前缀** `_name`：

```cpp
class Chunk {
private:
    Columns _columns;        // ≈ Java 的 this.columns
    SlotHashMap _slot_id_to_index;
};
```

> Java 中你习惯用 `this.field`，C++ 中看到 `_field` 就是成员变量。

## 4. 代码入口与启动流程

理解 BE 的启动流程是理解整个系统的基础。

### 4.1 启动入口：`main()` 函数

文件：`be/src/service/starrocks_main.cpp`

启动流程可以类比为一个 Spring Boot 应用：

```
main()
  ├── 读配置 (config::init)              ≈ Spring 读 application.properties
  ├── 初始化 curl / AWS SDK              ≈ 初始化 HttpClient
  ├── 解析存储路径                        ≈ 配置数据目录
  └── start_be(paths, as_cn)             ≈ SpringApplication.run()
```

### 4.2 核心启动函数：`start_be()`

文件：`be/src/service/service_be/starrocks_be.cpp`

```
start_be()
  ├── Daemon 启动（后台守护线程）         ≈ @Scheduled 定时任务
  ├── GlobalEnv 初始化（内存追踪等）      ≈ Spring ApplicationContext
  ├── StorageEngine 初始化               ≈ 初始化数据库连接池
  ├── ExecEnv 初始化（查询执行环境）      ≈ 初始化线程池 + 各种 Manager
  ├── 启动 Thrift Server（9060 端口）    ≈ 启动 gRPC Server
  ├── 启动 BRPC Server（8060 端口）      ≈ 启动另一个 RPC Server
  ├── 启动 HTTP Server                   ≈ 启动 Spring MVC 的嵌入式 Tomcat
  ├── 启动 Heartbeat Server              ≈ 启动心跳服务
  └── while(!exit) sleep(1)              ≈ 主线程等待关闭信号
```

### 4.3 两个全局单例

这两个单例是 BE 中最重要的"上下文"对象，几乎所有模块都依赖它们：

| 单例 | 获取方式 | Java 类比 | 职责 |
|---|---|---|---|
| `GlobalEnv` | `GlobalEnv::GetInstance()` | Spring `ApplicationContext` | 全局内存追踪器、进程级资源 |
| `ExecEnv` | `ExecEnv::GetInstance()` | Dubbo 的 `ServiceRepository` | 查询执行环境，持有各种 Manager、线程池 |

> **阅读技巧**：当你在代码中看到 `ExecEnv::GetInstance()->xxx_mgr()` 时，可以理解为 Spring 中的 `applicationContext.getBean(XxxManager.class)`。

## 5. 推荐阅读路径

### 路径一：一条 SQL 查询的生命周期（推荐首选）

这条路径帮你理解"一条 SELECT 查询是怎么在 BE 上执行的"：

```
1. service/  — RPC 接口接收 FE 下发的查询 Fragment
   └── 入口：internal_service.cpp 的 exec_plan_fragment()

2. runtime/fragment_mgr.cpp — Fragment 管理器，创建查询上下文
   └── 类比：TaskManager，接收任务并分配资源

3. exec/pipeline/ — Pipeline 执行引擎（核心！）
   ├── pipeline_builder.cpp — 将 PlanNode 树构建为 Pipeline
   ├── pipeline_driver.cpp — Driver 状态机，调度 Operator 执行
   └── operator.h — Operator 基类（push_chunk / pull_chunk）

4. exec/ — 具体算子实现
   ├── olap_scan_node.cpp — 从存储层扫描数据
   ├── hash_join_node.cpp — Hash Join 实现
   └── aggregate/ — 聚合计算

5. column/chunk.h — Chunk 数据结构（一批数据的载体）
   └── 理解 Chunk 是理解向量化执行的关键

6. storage/ — 存储引擎（按需深入）
   └── tablet_reader.cpp — 如何从磁盘读取数据
```

### 路径二：一条数据写入的生命周期

理解 INSERT / Stream Load 是怎么把数据写入存储的：

```
1. runtime/load_channel_mgr.cpp — 接收 FE 发来的数据
2. storage/delta_writer.cpp — 将数据写入 MemTable
3. storage/memtable.cpp — 内存排序表
4. storage/rowset/rowset_writer.cpp — 将 MemTable flush 为 Rowset
5. storage/tablet.cpp — 管理 Tablet 的 Rowset 集合
6. storage/compaction.cpp — 后台 Compaction 合并小文件
```

### 路径三：存储引擎内部

理解数据是怎么在磁盘上组织的：

```
1. storage/storage_engine.cpp — 存储引擎入口
2. storage/tablet.cpp — Tablet（≈ HBase Region）
3. storage/rowset/ — Rowset 和 Segment 的读写
4. storage/lake/ — 存算分离模式
```

## 6. 高效阅读技巧

### 6.1 先读 `.h`，后读 `.cpp`

C++ 头文件包含了类的 **完整接口定义**：所有公有方法、成员变量、继承关系、类型别名。对于"理解一个模块做什么"这个目标，**只读 `.h` 文件通常就足够了**。

```
阅读优先级：
1. .h 文件 — 接口、类型定义、注释（最重要）
2. .cpp 文件的函数签名 — 实现了哪些逻辑
3. .cpp 文件的函数体 — 具体怎么实现的（按需深入）
```

### 6.2 利用 `#include` 理解依赖

一个 `.cpp` 文件的 `#include` 列表就是它的"依赖声明"。通过 `#include` 可以快速判断一个模块依赖了哪些其他模块：

```cpp
// 看 starrocks_be.cpp 的 #include 列表，立刻知道启动过程涉及哪些模块：
#include "agent/heartbeat_server.h"        // Agent 心跳
#include "runtime/exec_env.h"              // 执行环境
#include "storage/storage_engine.h"        // 存储引擎
#include "service/service_be/http_service.h"  // HTTP 服务
```

### 6.3 跟踪 Status 调用链

遇到 `RETURN_IF_ERROR` 时，点击跳转到被调用的函数，沿着调用链一路追踪，就能理解一个操作的完整流程。这比 Java 中追踪异常栈更直观。

### 6.4 善用 `grep` / `rg` 搜索

```bash
# 查找某个类的所有使用
rg "TabletReader" be/src/ --type cpp -l

# 查找某个虚函数的所有实现
rg "has_output\(\) const" be/src/ --type cpp

# 查找某个配置项
rg "CONF_.*compaction" be/src/common/config.h
```

### 6.5 阅读测试代码

测试文件在 `be/test/` 目录下，和 `be/src/` 结构对应。测试代码通常包含：
- 类的基本用法示例
- 边界条件说明
- 各种参数组合

```
# 想理解 Chunk 怎么用？
看 be/test/column/chunk_test.cpp

# 想理解 Status 怎么用？
看 be/test/common/status_test.cpp
```

### 6.6 关注注释中的设计文档链接

BE 代码中部分文件包含指向设计文档或 Issue 的链接，这些是理解"为什么这样设计"的最佳资源。

## 7. C++ 语法速查（遇到时翻阅）

以下是你在阅读 BE 源码时可能遇到的 C++ 语法，按"遇到频率"排序：

### 7.1 极高频（几乎每个文件都有）

| C++ 语法 | 示例 | Java 类比 |
|---|---|---|
| `const` 成员函数 | `bool ok() const;` | 方法不修改对象状态（Java 无强制标记） |
| `auto` 类型推导 | `auto chunk = create_chunk();` | `var chunk = createChunk();`（Java 10+） |
| `->` 指针访问 | `ptr->method()` | `obj.method()`（Java 中引用和指针没区别） |
| `::` 作用域解析 | `Status::OK()` | `Status.OK()`（静态方法调用） |
| 引用 `&` | `const Chunk& src` | 参数传递，避免拷贝（≈ Java 的引用传递） |
| 右值引用 `&&` | `Chunk&& src` | 移动语义，转移所有权（Java 无对应） |
| `std::move()` | `return std::move(chunk);` | 转移对象所有权，避免拷贝 |
| Lambda 表达式 | `[this]() { ... }` | `() -> { ... }`（Java Lambda） |
| `override` | `bool has_output() const override;` | `@Override` |
| `nullptr` | `if (ptr == nullptr)` | `if (obj == null)` |

### 7.2 高频（多数文件会遇到）

| C++ 语法 | 示例 | Java 类比 |
|---|---|---|
| `using` 类型别名 | `using ColumnPtr = std::shared_ptr<Column>;` | `typedef`，无直接 Java 对应 |
| 初始化列表 | `Foo(int a) : _a(a), _b(0) {}` | 构造函数中赋值（但 C++ 语法不同） |
| `explicit` | `explicit Foo(int x);` | 禁止隐式类型转换（Java 没有这个问题） |
| `noexcept` | `~Foo() noexcept;` | 声明不抛异常 |
| `= default` | `Foo() = default;` | 使用编译器生成的默认实现 |
| `= delete` | `Foo(const Foo&) = delete;` | 禁止拷贝（≈ 不提供 `clone()` 方法） |
| `static_cast<T>()` | `static_cast<int>(x)` | `(int) x` 强制转换 |
| `reinterpret_cast<T>()` | `reinterpret_cast<char*>(ptr)` | 底层内存重新解释（Java 无对应） |
| 枚举 class | `enum class Color { Red, Blue };` | `enum Color { RED, BLUE }` |

### 7.3 中频（在特定模块会遇到）

| C++ 语法 | 示例 | 何时遇到 |
|---|---|---|
| 模板特化 | `template<> class Foo<int> { ... };` | `column/`、`exprs/` 中的类型分派 |
| `constexpr` | `constexpr int SIZE = 1024;` | 编译期常量（≈ `static final`） |
| `std::function` | `std::function<void()> callback;` | ≈ Java 的 `Runnable`、`Consumer<T>` |
| `std::optional<T>` | `std::optional<int> val;` | `Optional<Integer>` |
| `std::variant<T...>` | `std::variant<int, string> v;` | Java 没有（类似 sealed interface + record） |
| 位运算 | `flags & MASK` | 与 Java 相同 |
| `volatile` | `volatile bool _stop;` | 与 Java `volatile` 含义不同，用于防编译器优化 |

## 9. 常见问题解答

### Q: 看到 `std::move` 不理解怎么办？

**简单理解**：`std::move(obj)` 把对象的"所有权"从一个变量转移到另一个变量，转移后原变量不应再被使用。类似 Java 中把一个引用赋给另一个变量后把原变量设为 `null`。

### Q: `const Chunk& src` 和 `Chunk* src` 有什么区别？

- `const Chunk& src`：引用传递，不可修改，一定非空（≈ Java 的普通参数传递 + `@NonNull`）
- `Chunk* src`：指针传递，可能为 `nullptr`（≈ Java 的 `@Nullable` 参数）
- `Chunk&& src`：右值引用，表示调用者打算把对象的所有权转移给被调用者

### Q: 为什么到处都是宏？Java 没有宏。

C++ 宏在预编译阶段做文本替换，用于：
1. **减少样板代码**（如 `RETURN_IF_ERROR` 避免重复写 `if (!status.ok()) return status;`）
2. **条件编译**（如 `#ifdef USE_STAROS`，根据编译选项包含/排除代码）
3. **配置声明**（如 `CONF_Int32(be_port, "9060")`）

> **阅读技巧**：遇到不认识的宏，用 IDE 跳转到定义处看它展开成什么。

### Q: `auto&&` 是什么？

`auto&&` 是"通用引用"（universal reference），可以绑定到左值或右值。在 `RETURN_IF_ERROR` 宏中使用 `auto&& status__ = (stmt)` 是为了避免不必要的拷贝。初次阅读时可以简单理解为 `auto`。

### Q: BE 的线程模型是什么？

- **bthread**（百度开源的用户态线程）：用于 BRPC 网络通信
- **pthread**：用于 Compaction、数据写入等后台任务
- **Pipeline Driver**：Pipeline 引擎使用工作线程池调度 Driver，一个 Driver 不绑定固定线程
- **ThreadPool**：通用线程池，类似 Java 的 `ThreadPoolExecutor`
